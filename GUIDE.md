# The agentik guide: conventions shared by the tools (r1, 2026-10-13)

Binding on the five tools, agentik-session, agentik-decisions, agentik-respeak, agentik-relay and agentik-agents. Each works alone (R25-91 (3)); these make them consistent, not dependent. §1–§9 are agentik-session's `design/conventions.md` (r1, 2026-09-22) under the new names; that file keeps a pointer here. §10 is agentik-r1's table (`design/agentik-r1.md` §7.2).

## §1 Layout

```
agentik-<tool>/
  <tool>/ or go.mod  the tool (stdlib python or Go), on PATH as `agentik-<tool>` via `make install`
  plugin/  the plugin subtree, self-contained: names no path outside itself
    .claude-plugin/plugin.json
    skills/<name>/SKILL.md  frontmatter: name, description under 200 chars, allowed-tools; body under 500 lines
    commands/<verb>.md  one verb each, under 30 lines
    agents/<name>.md  only where the plugin owns a lane
    hooks/hooks.json  events, by the shim below or the plugin's own scripts
    hooks/run  optional: execs `agentik-<tool> hook <event>` on PATH, else exits 0
    hooks/<name>.ts  optional: the Mod, one `"modules"` entry (§4)
  design/  records `<topic>-rN.md`; packets/ ; readme/source.md
  history/sittings/  charters `<date>-<n>[-<chain>].md`, §3.1 shape (§5)
  scripts/agentik, hygiene, bounded, plugin-version-check, plugin-description-bytes  vendored from agentik-commons, pinned in scripts/vendored.sha256 (§5)
  scripts/doclint  the doc gate (§5)
  tests/  the suite (§4)
  Makefile  check, test, lint, doclint, hygiene, validate, readme, install, doctor
  README.md LICENSE .hygiene-allow .gitignore
  relay/queue.yaml  only while the relay runs this repo (D4)
```

A tool repo keeps no `marketplace.json` of its own: two install paths would double the hooks (§2).

A plugin's descriptions stay at or under 1,024 B in sum, since the description of every skill, command and agent type the model may start is in the context of every main session, and of every helper whose agent type holds the Skill or Agent tool, on every request (hq design/09 §2, F7); the vendored `scripts/plugin-description-bytes plugin` measures them in `make check`. A command only the owner types sets `disable-model-invocation: true`: typed, it runs as before, and its description leaves the context. An agent type that needs neither the Skill nor the Agent tool lists its `tools`, so its sessions carry no descriptions.

## §2 plugin.json and marketplace.json

`plugin.json`: `name` (the short id: `session`, `decisions`, `respeak`, `relay`, `agents`; installed as `<tool>@agentik`), `version` (semver; §7), `description` (under 200 chars, no owner data), `author {name}`, `homepage`, `repository`, `license`, `keywords`; `dependencies` only where needed, in either form Claude Code accepts, a bare name or `{name, version, marketplace}` with an npm range; `suite` uses bare names, since a `^` range matches no prerelease such as `2.0.0-alpha.43`; `userConfig` only for install-time knobs (repo config is §3). The one marketplace is agentik-commons' `.claude-plugin/marketplace.json`: `name` `agentik`, `owner {name}`, `plugins: [{name, source: {source: "git-subdir", url, path: "plugin"}, description}]`, one entry per tool, then a sixth, `suite`, commons' own plugin on commons' own url with `path: "plugins/suite"`: the suite's default set, whose `dependencies` install session, decisions and agents (hq design/04 §5), and the `agentik-suite` command that manages it, checked by `scripts/marketplace-check`. The owner's machine installs from `make local-marketplace`, the same file less `suite` with `file://` urls, so the IDs match, plus after the five the entries of the owner's overlay (`AGENTIK_MARKETPLACE_OVERLAY`, default `~/.config/agentik/marketplace-local.json`, outside every repo) for a plugin whose repo is not public, which the published file never names.

## §3 Configuration layering, the session as optional provider

Each plugin resolves its own configuration, lowest first: shipped defaults; the user's file (`~/.config/agentik/<tool>/config.yaml`); its section of the repo's `.claude/agentik/config.yaml`; `config.local.yaml` beside it (gitignored); folder and scope files where it has them (respeak); the session's resolved file when present; its session toggles; the invocation.

The resolved file: `${XDG_STATE_HOME:-~/.local/state}/agentik-session/sessions/<session_id>/resolved.json`, written only by `session` at SessionStart and on `set`, shaped `{"provider": {plugin, version, profile, resolved_at, inputs: [{path, sha256}]}, "<plugin>": {..}}`. A plugin takes `session_id` from hook stdin or `$CLAUDE_CODE_SESSION_ID`, the only session variable it reads, accepts the file only when `provider.version` is in its range, applies its section as the layer above, never writes it, and reports it in `doctor`. A plugin reads it only while fresh (agentik-relay's AR75, session-layer-r1 §2): `provider.inputs` lists the plugin's own repo file and the `config.local.yaml` beside it, compared as absolute paths after cleaning, each at the sha256 that file has now (a null matches only a file still absent, an unreadable file has changed); a changed input, inputs that name another checkout's files, or no or a malformed `inputs` makes the layer stale, and the plugin then skips it whole, keeps its own repo and local layers, and gives one warning naming the layer and why, which `doctor` shows as a warning, never a failure. Absent, it runs alone.

The session's own, no dependent's: `CLAUDE_SESSION_DEPTH` (`start` sets parent plus one past its scrub, refuses 2 without `--nested`; the relay sets 1 for its children) and `CLAUDE_SESSION_MAX_TURNS` (set by `start --max-turns`; the turn ceiling is the smaller of it and the profile's). A new variable is named `AGENTIK_*` (§10).

Config files are YAML in the strict subset (D12): mappings, scalars, flat lists, comments. Unknown keys: reported by `doctor`, never fatal.

## §4 The test standard

- **Go** (relay, example-app): table tests over every transition of a state machine; every effect (git, spawn, clock, files) behind a faked interface; an end-to-end test against a fake `claude` of canned stream-json; `go vet` and the race detector in `check`; no network in tests.
- **python** (session, decisions, respeak): stdlib, from `tests/`; a fake `claude` on a temporary PATH, never quota; every hook tested per event from a stdin fixture, exact stdout and exit; the resolver tested per layer pair; byte ceilings tested, not assumed.
- **Mod** (`plugin/hooks/*.ts`): one module per plugin holds every concern (2.1.296: one unmatched hook per event, `$` into no import); `.test.ts` beside it, effects faked, run in `check` by `claude plugin test plugin` (no model); pytest never reads it.
- Every invariant in a design's provability section is one named test; one that can also be a runtime guard is both, the test naming the guard.

## §5 `make check` and the doc gate

`check` runs under `scripts/bounded --lock .check.lock --wall 840 --load 4`: `test`, `lint`, `doclint`, `hygiene`, `validate` (60 s), README freshness (§6), `shasum -a 256 -c scripts/vendored.sha256` (in a repo with a `plugin/lib/`, it also lists the placed `install-cli` module, launcher and door, §10, so a one-byte change in any of them is red), `scripts/plugin-version-check` (§7) and `scripts/plugin-description-bytes plugin` (§1). The load rule, as `scripts/bounded` has it: while the 1-minute load is above 4 per core and the CPU's idle share is 25% or less, `bounded` holds the start, polling every 30 s, and after 600 s or at the wall, whichever comes first, exits 2 without running the command; an idle share above 25% at the first reading lets the command start at any load (two readings in a row once it waits), and an unreadable one leaves the load alone to decide. The wall counts from `bounded`'s start, the load wait included. A repository may raise its wall in its own `check` line, kept under the gate's verify limit (the relay's `verify_seconds`, 900 s when unset) so that the wall's stop, read as unrun, comes before the gate's cut; the relay's own `check` keeps 840 s. The lock is a `flock` held by a guardian that kills the command's group when `bounded`'s pipe closes, SIGKILL too. A last stderr line `bounded: stop: lock|load|wall` (exits 2, 2, 124) is unrun, never red; under another `bounded` (`BOUNDED_DEPTH` above 0) it is `bounded: nested stop:`, a plain red. `doclint`'s rules are its docstring: byte ceilings, `NEXT` only as `history/sessions/NEXT`. A packet's `verify` row is the gate line (`make check`); acceptance lines are targeted, rerun by the gate on the branch; doclint's suite rule fails closed from any runner word, passing only a test file, `::`, a `-k`, `go test <pkg> -run <Name>`, `make -n`, or `make` of `MAKE_TARGETED` targets. Packet prompts keep the turns line (`Your --max-turns is N`) until the doctor reads the meter hook live. `pluginlint` is retired at each repo's next re-sync.

## §6 README via respeak, and hygiene

`design/readme/source.md` holds the facts in the technical lane; `make readme` renders `README.md` in respeak's technical mode (`claude -p` or respeak's own script); the invariant is the sidecar `design/readme/rendered.sha256`, not the renderer: two `shasum -a 256` lines (source, README), both from `make readme`. Edit the source, never the README. A README names dependencies by id and range, nothing else outside the repo; no owner path, address, domain, private repo or person in any tracked file. `scripts/hygiene` scans each line, path and link target for its generic groups (home, lan, sibling, secret, email, renamed) and the private list's, owner terms kept outside the repo (`$AGENTIK_HYGIENE_PRIVATE` or `~/.config/agentik/hygiene-private.tsv`); absent: one warning, exit 2 under `--require-private`. `renamed` reads the live files only (agentik-r1 §6.1): outside `design/`, `bugs/` and `history/` and not a `NICE_TO_HAVE.md` or `CHANGELOG*`, plus `history/sessions/PROMPT-*` and `BRIEF-*` and the newest charter of each running chain. A repo declares its running chains in `.hygiene-live`, one chain per line, `-` for the unsuffixed chain; no file means no charter is live. `--json` gives each group `lines` and `files`, allowlisted hits included, and `outside_lines` and `outside_files`, the hits outside the allowlist only; a count of zero is read from `outside_files`. `.hygiene-allow` has exceptions, each row under a `#` reason line (`secret` only under `tests/fixtures/`; `sibling` skipped under `history/sittings/`); counts only, no match or private regex; exit 1 on a hit, 2 on usage. `--commits <range>` scans a range's added lines and messages instead, under the head's allowlist; before a push, `scripts/hygiene && scripts/hygiene --commits origin/main..main`. The canonical `scripts/hygiene`, `scripts/bounded` and `bin/agentik` live in agentik-commons; `scripts/sync <repo>` there copies them in and writes `scripts/vendored.sha256`; `scripts/sync --check <repo>` writes nothing and prints `behind <path>` for a copy absent or unlike commons' in bytes or mode and `unlisted <path>` for a manifest that lacks or adds a path, the tool's own `agentik-tool.conf` and `messages.md` never compared: exit 0 every copy is commons', 1 a line, 2 usage or a refusal of the write path's. `scripts/doclint` stays byte-identical across the repos, sha256 `26eaf2c84aadb822f8d63a0257b063afcc0ba6d9bbcf1d2d856abe4c6388341f`, until r2 makes it one copy. Nothing is pushed red; the owner pushes (R25-91 (4)).

`agentik session gate land` and `gate publish` scan by the repo's own targets where the makefile make reads (`GNUmakefile`, `makefile`, then `Makefile`) has them: `make hygiene` for the tree, in place of the bare `scripts/hygiene`, and `make hygiene-range RANGE=<a>..<b>` for a span of commits (a branch's, a merge message's), in place of `scripts/hygiene --require-private --commits <span>`. A `hygiene` target scans the working tree and exits non-zero on any hit by the repo's own rules; a `hygiene-range` target scans the commits of `$(RANGE)` with the private list required, and exits non-zero on any hit and on an empty `RANGE`. Each is named in `.PHONY`, has a recipe, and holds no scanning line led by `-`, no line led by `+` and no `$(MAKE)`: the land step first asks `make -q <target>` whether a recipe would run, and a target that would run none is red, never a skipped scan. A repo with neither target is scanned by the bare script, as before. A repo whose `hygiene` target is more than the bare script (a wrapper, words of its own left out) needs `hygiene-range` too, or its spans are still read by the bare script.

## §7 Versioning and the sitting record

Semver; `0.x` may break on a minor and says so in the tag message; a change to a config key, a hook's output, or the resolved-file contract bumps the major; a release's tag `v<semver>` equals `plugin.json` `version`; a `-alpha.N` version needs no tag (and matches no `^` range); the session widens a dependency range only once its suite passes against it. Any change under a plugin's `plugin/` bumps `plugin.json`'s version, an `-alpha.N` included, since Claude Code refreshes an installed plugin only on a new version: `scripts/plugin-version-check` fails when a file under `plugin/` changed after the commit that last changed the version (a bump not yet committed passes). Sittings carry a charter, commit per act, never `--amend` or push, builders in worktrees (at open, before `make`, `.venv` a symlink to the main checkout's; `make venv` only where it has none); a worktree never writes under `.venv` (no `pip install -e`: E7). A repo not yet moved under hq design/04 keeps this paragraph; a moved one takes §10's `install-cli`. `make install` freezes the committed `<tool>/` by tree hash and runs it with `python -P` (floor 3.11): no checkout runs hooks (T5); it also installs the `agentik` front door from the vendored `scripts/agentik` (D3). The launcher bakes the venv's `bin/python` link (its directory resolved), never the link's target; a `/Cellar/` path is refused. When that interpreter or the frozen tree is gone, a hook says `run make install` once and exits 0; other verbs exit 1. Scripts keep `#!/usr/bin/env python3` (T3: the owner's global line names the exception); gate lines run under `make` or `.venv/bin/python`, never a shim.

The `stamp` target is opt-in: where a Makefile has one, `agentik session gate land` readies a branch behind main (it merges main, then stamps); a repo without one is landed as it stands. Against `STAMP_BASE` (default `main`), `make stamp` writes the next version (main's last number plus one; `STAMP_VERSION=` overrides and must be above main's), the README Status line's version and test count, and the README sidecar by `shasum`, and moves the oldest S4 rows of `NICE_TO_HAVE.md` to the overflow until the file is under recordlint's bound. It changes nothing else, and a second run changes nothing. After a merge it is red when the merged count is not the branch's plus main's less the merge base's. A builder runs it before its own gate. The job takes only derived lines of a conflict: the `"version"` line of `plugin/.claude-plugin/plugin.json`, a line beginning `Status: version ` in `README.md` or `design/readme/source.md`, any line of `design/readme/rendered.sha256`, and a row of `NICE_TO_HAVE.md` or `history/NICE-overflow.md` (merged by id); a conflict on any other line stops the landing (`red behind`). Each commit the job writes closes with `Gate-Land: <sha given>`; the last is the stamp commit, `<branch>: plugin <version>`.

## §8 Citing a record

Packets and sitting prompts' read lists cite a record as `record <file> --section SPEC` lines (overhaul-r1 §2.7), never a prose range; READMEs cite sections likewise.

## §9 Packet authoring

- **may touch** is a closed list of full paths from the repo root; it always admits `history/sittings/*.md` and `history/sessions/NEXT`.
- The `verify` row is required (doclint's GRANDFATHERED excepted: 11 in agentik-session, 17 in agentik-relay); each **acceptance** line is targeted (§5; relay's `packet.Unbounded` takes the same cells), with a measured baseline. SPENT (relay's `spent`, ar21) keeps the row, skips the suite rule. In the table every pipe is `\|` (the gate unescapes), so alternation is `grep -E` with a plain `|`; fixed strings, `grep -qF`.
- Six sections, six header rows plus `verify`, under 9,216 bytes. One recorded exception (2026-10-14): commons' spent packet `design/packets/agentik-r1-commons.md`, 9,913 bytes, kept as it was built, since a spent packet is a record.
- A packet's charter opens with doclint's five rows; the budget row says so.
- The builder decides inside the design of record, records each choice in the charter's handover with its consumer, and names at most one open fork for the owner.
- A sitting's records (the merge message to a file outside the repo, the note under `history/sessions/`, the record commit by explicit path) go through the agents plugin's `agents:scribe` by default, where the plugin is installed, on Sonnet, from the hand-back, the repo and the records wanted; the coordinator reads its six lines (a-s14, 2026-10-29; a-s15, 2026-10-31).
- **Records are tables** (hq design/05 §2). `HANDOFF.md`: a title, one head paragraph, `<!-- decisions: build order -->`, `## The build order`, then one table, `| # | item | level | repo | where | state |`. `#` is the item's for life, a new one the highest ever used plus one, `history/handoff-done.md` included; row order is the build order; `item` at most 80 characters; `repo` is `hq`, a tool's short name or `suite`, bare; `state` opens `open`, `building <row>`, `waiting: <on what>` (exactly one of `owner <n>`, `row <n>`, `the owner: <text>` or `<repo> <branch>`, then optionally `; <text>`), `watch: <the sighting>` or `done <date> <sha>`, and a done row leaves, in the commit that marks it, as one line in `history/handoff-done.md`. `NICE_TO_HAVE.md`: a title, one head paragraph naming the archive, then tables under `##`, each `| id | level | area | finding | evidence | from |`: `id` `n<k>`, never reused; `level` `S1` to `S4`, S4 when unsure; `area` a component or a backticked path; `evidence` a `file:line`, sha, record, repro or "not confirmed"; `from` a date and source; a row leaves when it lands. A cell is one line, no list, no `<br>`, and every pipe in it is `\|`, code spans too; what does not fit goes to a cited file under `history/sessions/`. `scripts/recordlint` holds both (a row at most 400 characters, `HANDOFF.md` under 8,192 B, `NICE_TO_HAVE.md` under 24,576 B, the oldest S4 rows moving to `history/NICE-overflow.md`); `sync` vendors it, and a file without its header is skipped.
- **A row's records are a folder.** A tree's hq keeps one folder a build row, `history/rows/<row>/`, named as the row's branch is; `agentik decisions rows` reads each row's stage from it and from git, and nothing else says where a row stands. It holds `row.md`, `brief.md`, `build-<n>.md`, `review-<n>.md` and `merge.txt`. `row.md`, each build and each review opens with a two-column table, `| item | value |`; the tool reads that first table alone, each cell by its opening words with backticks dropped, and the rest is prose. `row.md`: `repo` (`hq` for the hq itself, else a tool's short name, found beside the hq as `agentik-<name>` or `<name>`), `level` (`S1` to `S4`), `from` (`HANDOFF <n>`, `<repo> n<k>`, `design/<nn> §<s>` or `review <row> <finding>`), `base`, `depends_on` (row names, or `none`), `done` (empty while the row is open; then `<date> <sha>`, the landing's merge on main's first-parent line, any commit on it for an `hq` row, or `withdrawn <date>: <why>`), and `branch` only where the branch is not named as the folder is; under the table, `## Owed`, a checklist of what the hq owes once the row lands. `agentik decisions rows close <row>` writes `done`, once asked or with `-y`, and commits nothing: with `--withdrawn <why>`, `withdrawn <date>: <why>` in `row.md` alone; else it refuses a row whose stage is not `pushed` or that has a box open under `## Owed`, and writes the landing's `<date> <sha>` in `row.md` and the row's line in the hq's `history/handoff-done.md`, both or neither, or `row.md` alone where that file already holds the landing's sha. `build-<n>.md`: `stage` (`first build`, `fix of review <k>`, `phase 2` or `cut`), `head` (a sha on the branch), `gate` (`<id> exit <code>`, `<id> running` or `none: <why>`). `review-<n>.md`: `slice` (`<base sha>..<head sha>`), `blocks` (finding ids, or `none`), `ruling` (empty until ruled; then it opens `closed` or `fix`). `merge.txt` is the landing's message, its first line `Merge <row>: <text>`. No one types the stage: the tool derives one of `briefed`, `waits`, `building`, `built`, `to rule`, `to fix`, `reviewed`, `ready`, `landed` and `pushed`, and `rows check` reds a record that git contradicts and a `level` that its `from` contradicts. The folder is the hq's own: a packet, a charter and a commit message in a tool's repo name the row and never the folder's path.

**The floor (hq entry 6).** A Python plugin, as it moves under hq design/04, runs its hooks and tools from its own `plugin/lib` through a launcher in its `plugin/bin`, on `AGENTIK_PYTHON`, else `/usr/bin/python3`, else `python3` on PATH, at a runtime floor of Python 3.9 on the standard library alone, and a runtime script in it takes a `#!/usr/bin/python3` shebang. The floor binds a repo from its first packet under that design; until its move a repo stands as it is. A repo's own dev scripts and gates keep `env python3`.

**`install-cli` (hq design/04 §2, §3, §5).** The optional step that puts a moved tool's launcher on the terminal's PATH, with no checkout or venv. `<tool> install-cli [--prefix P]` freezes the code it runs from by content hash under `<prefix>/share/<tool>/<hash>/` (default prefix `~/.local`), writes `<prefix>/bin/<tool>`, a link for the tool's old name only where that name is a link in the bin folder already, and the `agentik` door, each by a temp file and a rename, then prunes: it keeps the new tree, each tree a running process names, and the newest three, and on any doubt about `ps` it removes nothing. The canonical forms are commons' `scripts/agentik_install.py` and `scripts/plugin-launcher`; `scripts/sync` places them at `plugin/lib/agentik_install.py` and `plugin/bin/agentik-<tool>`, with the door at `plugin/bin/agentik`, byte-identical in every tool and listed in `scripts/vendored.sha256`. `sync` places them only where the repo has a `plugin/lib/`; a `plugin/` with no `lib/` (the relay, respeak) gets the same set as a repo with no `plugin/`, so a tool's move makes `plugin/lib/` before its first sync. A placed copy under `plugin/` needs a version bump like any other change there (§7), and a re-sync that changes one is a bump. The module's `uninstall(tool_name, prefix, door, dry, spare)` takes the install back, for a verb to call: the launcher, each link in the bin folder whose text is the tool's name or that resolves into its share, the frozen trees (real folders of `_freeze`'s name) with any staging folder and the lock, the share once empty, the default prefix's `install-needed` marker, and with `door` the door where no other `agentik-<word>`, a file or a link, stands in the bin folder. It removes only what reads as install-cli's: a launcher that is no regular file, is 64 KiB or more, lacks the template's second line (or, for the session tool, the one its own install-cli wrote before its alpha.127), holds the text `TREE=` or the text `VERSION=` other than once in the whole file, has a `TREE=` line that is not `TREE=` and its value quoted as the template quotes it (`shlex.quote`), nothing after, or names a `TREE` outside the share keeps every row, as does a share that is no real folder at its own place or a `.lock` that is no regular file; a running process that names any path in the share, or a `ps` it cannot read, holds every row, read before the lock and again under it. The walk of a tree and the open of `.lock` follow no link, it removes nothing outside the bin folder, the share and the marker, a call that removes nothing leaves the disk as it was, and it returns each path with `removed`, `would remove` (with `dry`) or `kept` and why, `kept: partly removed` for a tree a failure cut short. Once `_lock` holds the lock it checks that `.lock` still names the file it holds and takes it again where it does not, so a waiter on a `.lock` an uninstall removed holds no lock another cannot see; a tool's copy of the module older than this lacks that check until its next sync. `agentik remove PLUGIN...` (packet ak4-remove) runs `claude plugin uninstall <name>@agentik --keep-data` for a plugin setup installed, then this `uninstall`, and lists each config and state folder and Claude Code's data and cache folders for the tool as kept, each folder once (`--all` adds the suite's own cache folder where it stands); a plugin setup did not install is kept with its command. `remove --all` then uninstalls the suite's plugin, and only then removes the `agentik` marketplace where it is the one setup adds, so every plugin goes before its marketplace; then the suite's launcher, trees and the door (the dry run's reason for a door kept names the entry the run finds standing), and `${XDG_CACHE_HOME:-~/.cache}/agentik` where it is a real folder at its own place, so config and state are what it leaves; it is held as `update` is, and asks as setup does.

**The writer, `term` (hq design 15's P7, packet ak10b-term).** Every byte a person reads leaves a tool through one writer module, `term`, as it leaves the suite. Where the repo has a `plugin/lib/`, `scripts/sync` places it as the package `plugin/lib/agentik_term/`: `term.py` and `catalogue.py`, byte-identical to the suite's own under `plugins/suite/lib/agentik_suite/` (commons keeps one copy of each, the suite's), and an `__init__.py` whose bytes `sync` writes; all three are listed in `scripts/vendored.sha256`, and a re-sync that changes one is a bump (§7). A tool's code reads `from agentik_term import term`, its runner having put `plugin/lib` on `sys.path`. Beside them, `plugin/lib/agentik_term/messages.md` is the tool's own catalogue, never listed: `sync` writes it once, when absent, by a temp file and a rename, with a title, a line saying whose it is, and each message id `term.py` names itself (today `err.next`) with the suite's text for it, and never writes it again; the tool adds its own messages there by id. `Term` raises on a catalogue it cannot read (`messages.md` missing, not a file, or lacking an id the writer names), so a tool's runner catches that and prints `term.unreadable`'s line. A tool takes its own voice gate, hq design 15 §5.3's `make voice` and its sidecar, in the row that first moves a verb onto `term`.

|---|---|
| the catalogue, `plugin/lib/agentik_term/messages.md` | the tool's own: `sync` seeds it once when absent and never again; not listed |

| exits | |
|---|---|
| `install-cli` | 0 done; 1 it could not, one line on stderr, a malformed conf included |

**The forward-only refresh.** On SessionStart, a plugin newer than the launcher that exists runs the install. It creates no launcher; it refuses a backward or equal version, a version it cannot read, and a link; only the plugin `CLAUDE_PLUGIN_ROOT` names refreshes, never a frozen tree or a checkout; another process holding the lock costs nothing, since a later session sees what it left; and a failure is one line for the `systemMessage`, never a failed hook. `install-cli` by hand may go backward: it is the way down.

**`AGENTIK_ARGV0`, the word typed (commons row sc2).** The root `setup` and the plugin launcher `sync` places set it to the word they were started with, the launcher only where it is unset, so setup's word passes through; the launcher `install-cli` writes sets none. Only the suite reads it, to start the commands its lines print, and drops it from what it spawns. Every other tool's children, sessions and hooks included, inherit it; that is harmless, since the suite takes a word only where, from the working folder, it still names the same file (`samefile`) as the checkout's `setup` or the plugin's launcher, and else prints the launcher's absolute path.

**Completion (row ak12-polish).** `agentik completion zsh` and `agentik completion bash` print a short script and write nothing: a person adds `eval "$(agentik completion zsh)"` to `~/.zshrc`, or the bash line to `~/.bashrc`, and `agentik help completion` shows both. The script holds no word. An empty answer falls to the shell's own file completion.

**The aliases.** Through r1 the old names keep working as aliases (agentik-r1 §4.3), and r2 ends them on or after 2026-12-31: `claude-code-session`, `claude-code-decisions`, `claude-code-respeak`, `claude-code-agents`, `agent-relay`, `claude-session`, `claude-local`, `claude-agents`, `localrig`, `agentroute`, and the bare `` `relay <verb>`` and `` `decisions <verb>`` forms. A new machine gets none of them: `install-cli` refreshes an old name's link where one stands, writes no new one, and never writes over a file that is not a link. `claude-api-agent`, `claude-fanout` and `claude-costs` ended on 2026-10-31 with the verbs they named, on the owner's word (agentik-agents a-s17). An alias gives one note on a terminal and nothing new in hooks or pipes (A3). New text uses only the new names; the `renamed` group holds every live file to that, and this guide's row in `.hygiene-allow` covers this paragraph.

## §11 The plug: what a tool prints so the suite can read it

A tool joins `agentik config`, `agentik doctor`, `agentik status` and `agentik inbox` by printing four kinds of JSON answer: its `describe --json`, a config read, a doctor read and any number of status reads. Each rule below says what the suite's reader does with a key; where the reader reads nothing in a key, the rule says what a tool prints and that the suite ignores it. The exit codes are §10's; the config layers' place is §3's.

### §11.1 How the suite calls a tool

- It runs the file that runs for the tool and nothing else: the first `agentik-<tool>` on PATH that is a regular executable, passed over when it lies under the root of a plugin that does not stand for the tool, else the standing plugin's `bin/agentik-<tool>`. `config`, `doctor` and the claims find the file so. `status` and `inbox` ask only a tool whose `agentik-<tool>` is on PATH, so a tool that a plugin alone installs is never read by them: `status` runs PATH's file, or the file the finder says runs where it passes that one over, and none where nothing runs; `inbox` runs PATH's file. A read's `argv` is the words after that file.
- stdin is `/dev/null`; stderr is thrown away, save a status read's first line (§11.6); the environment and the cwd are the caller's, so "the repo" is the cwd's repo. Each process starts in its own group, and the group is killed when the process exits or at its wall, so nothing it starts outlives the read.
- `describe --json` and the config read share **one wall of 2 s**, set at the first spawn, over every tool at once: a tool's config read starts as soon as its describe answer is known and ends inside the same wall. A read still running at the wall, or not started by it, reads as `timed out`.
- A `describe` answer that counts is cached in `${XDG_CACHE_HOME:-~/.cache}/agentik/suite/<tool>.json` while the file's resolved path, size and modified time (in nanoseconds) hold. An answer that does not count is never cached, and neither is a config, doctor or status read. So a tool's two reads together stay well under 1 s on a busy machine, and each tool's test bounds one read at 1 s.
- stdout past 1 MiB is cut, and the read reads as `unreadable`; so does a file that cannot start.
- The doctor read has a wall of its own: after the describes' 2 s, one deadline of 30 s over every tool's doctor reads at once, a second round included (§11.5).
- A status read, and each describe the status asks, has a wall of 1 s from its own start, save a fallback table's read that names its own.

So the `describe` read and the config read start no model and no `claude`, open no socket, prompt for nothing, and write nothing outside `${XDG_CACHE_HOME:-~/.cache}/agentik/`. A status read starts no model and writes nothing outside that folder either. The doctor read is held to §11.5's bounds instead: it may start `claude --version` or a `claude plugin` list, and it may write the tool's own state. Every read prints **one JSON object and a newline on stdout, UTF-8, no escape byte, nothing else**. Notes go to stderr.

Python's bytecode counts as a write. A read that runs under Apple's `/usr/bin/python3` with no prefix set writes files under `~/Library/Caches/com.apple.python` in a new HOME. So a read's interpreter is started with `-X pycache_prefix=${XDG_CACHE_HOME:-$HOME/.cache}/agentik/pycache`, as the vendored launcher starts it, or with `PYTHONPYCACHEPREFIX` set to that folder.

### §11.2 The envelope

Every answer opens `{"schema": "agentik.<read>/1", "ok": true, "tool": "<name>", ...}`. `tool` is the name less `agentik-`: a describe answer whose `tool` is another name does not count, and the list says its command answers under another tool's name; the suite reads no other answer's `tool`. A new key never raises the number, and a reader ignores a key it does not know. The numbers that count: a describe answer at `agentik.describe/1` alone; a config answer at `agentik.config/<n>`, `n` at most 1; a doctor answer at `agentik.doctor/<n>`, `n` at most 1, from the doctor read a describe names, and at `agentik.doctor/1` alone from the `doctor --json` the suite asks a tool that names none. A config or doctor answer above 1 does not count. A status read's `schema` above 1 marks its part changed, and the part is still read (§11.6).

A read that could not run prints, still on stdout, and exits 2:

```json
{"schema": "agentik.config/1", "ok": false, "tool": "demo",
 "error": {"code": "bad_file", "message": "/home/u/.config/agentik/demo/config.yaml:7: a tab in the indent", "remedy": null}}
```

`code` is a lowercase word with `_`; `message` is one line holding the file and line where there is one; `remedy` is a command a person can run, or null. The suite reads a config read's error whatever its exit: an object of the config schema, `ok` false, whose `error` is an object with a string `code` and `message` and a `remedy` that is a string or null; else the read reads as `unreadable`. It shows `code` and `message` as one line each, cut at 300 characters, and reads as null a remedy past 300 characters or holding a control or format character. `ok: true` means the read ran, never that what it found is good; a describe or config answer counts only with exit 0 and `ok` true.

### §11.3 `describe --json`

The one fixed argv. `describe` with no `--json` exits 2 with one line naming `describe --json`; an unknown word after `describe` exits 2.

```json
{"schema": "agentik.describe/1", "ok": true,
 "tool": "demo", "version": "1.2.0",
 "summary": "Paints each line of a report in the colour its level asks for.",
 "repo": "example/agentik-demo", "plugin": "demo@agentik",
 "needs": [{"name": "git", "kind": "program", "why": "reads the cwd's repo", "optional": false}],
 "verbs": [{"name": "paint", "summary": "Paint a report.", "top": false},
           {"name": "queue", "summary": "List the reports waiting to be painted.", "top": false},
           {"name": "describe", "summary": "Print what the suite reads of the tool.", "top": false},
           {"name": "doctor", "summary": "Check the tool and what it needs.", "top": false},
           {"name": "install-cli", "summary": "Place the tool's command on PATH.", "top": false}],
 "reads": [{"kind": "config", "name": "settings", "argv": ["describe", "config", "--json"]},
           {"kind": "doctor", "name": "doctor", "argv": ["doctor", "--json"]},
           {"kind": "status", "name": "run", "argv": ["queue", "--json"]}]}
```

| key | type | rule |
|---|---|---|
| `version` | string | what `--version` prints after the name; `help` shows it, and the list's `config --json` where the finder knows no source for the tool or the one standing is the marketplace's own; for any other source (a plugin of another marketplace, a folder, or candidates of which none stands) that `version` is null |
| `summary` | string | one sentence, under 80 characters, what the tool does for its user; `help` and `config --json` show it |
| `repo` | string | `<owner>/<repo>` of the public repo; the suite needs the key and ignores its value |
| `plugin` | string or null | `<name>@agentik`; null for a tool with no plugin; the suite needs the key and ignores its value, since its finder says which plugin stands |
| `needs` | list | what must be on the machine for the tool to run. `kind`: `program` (an executable on PATH), `package` (a Python package), `plugin` (a `<name>@agentik`) or `toolchain` (needed to build it). `why`: a clause. `optional`: true when the tool runs without it and says so. The suite needs a list and ignores its rows |
| `verbs` | list | every first-level verb, in help's order; `summary` is help's own line for it, which the suite ignores. `top` true claims `agentik <verb>` for this tool (below): false unless the verb is a first-level verb of the tool's own that a person would type bare. Of the names the suite reads one, `install-cli`: a tool that has `install-cli` (§10) lists it, `setup`'s launcher step reads that name, and a tool whose list names no `install-cli` is taken to run from its plugin's own folder, so the step places nothing for it |
| `reads` | list | each other read by its argv. `kind` `config` and `doctor`: at most one each, with the names and argvs above, the same in every tool; the suite runs the `argv` a read names, and a doctor read whose `argv` is empty is none. `kind` `status`: any number, each naming a read the tool already has, drawn by its `name` (§11.6). A status read may carry `wall_s`, a number above 0 and at most 10: its wall in seconds in place of 1 s, and a read without it gets 1 s; a reader that does not know the key ignores it (§11.2), so the schema stays. The suite takes `wall_s` from a tool's answer once its fallback table is gone; until then it reads the table's own |

The suite refuses the whole answer, and the tool reads as `unreadable` with no config read, no claim and no doctor read of its own, when the exit is not 0, stdout is not one JSON object, `ok` is not true, `schema` is not `agentik.describe/1`, `tool` is not the name the suite asked under, `tool` or a key of the table is missing, `needs`, `verbs` or `reads` is not a list, a read is not an object, its `kind` is another word or its `argv` is not a list of strings, or two reads are `config` or two are `doctor`.

**The claim.** A `verbs` row `{"name": "<word>", "top": true}`, `top` the JSON `true` and the word a name (a lowercase letter first, then lowercase letters and digits, parts joined by `-`; a word of another shape claims nothing, and no line names it), claims `agentik <word>`; a tool claims a word once however often its list names it. `agentik <word> ...` reads the claims only where the word comes first and nothing else settles it: no suite verb, no tool's name and no plugin's name. A claim counts where the tool's standing source is its plugin from the agentik marketplace and a file runs; where the word is none of the suite's verbs (`help`, `version`, `setup`, `update`, `config`, `describe`, `status`, `install-cli`, `doctor`, `inbox`, `issue`) and none of the words `doctor` reserves (`remove`, `update`, `init`, `completion`, `inbox`), so a suite verb is never handed to a tool; and, for a word the suite keeps for one tool (`rows`, kept for the decisions tool; `guard`, kept for none yet), where the tool is that one. One claim of a word that counts: the suite runs the claimant's file as `<file> <word> <later words unchanged>`, in its own place, printing nothing. Two tools whose claims of one word count: neither runs, `agentik <word>` exits 2 naming the word and the tools, and `doctor` fails one `claim` check. A claim that does not count never runs, and `config <tool>` says why under the tool's list, where the finder knows a source for the tool (`config <tool> --json` carries each claim as `{verb, counts, reason}`; the list's `config --json` carries none): the suite keeps that word, keeps it for another tool, or the tool is not from the agentik marketplace. The claims are read from the describes under the 2 s wall, the cache's included; a tool whose describe does not count claims nothing.

### §11.4 The config read: `describe config --json [KEY]`

The suite runs the config read's `argv`, `KEY` after it when one is asked.

```json
{"schema": "agentik.config/1", "ok": true, "tool": "demo",
 "layers": [
  {"name": "default", "path": null, "present": true, "travels": false},
  {"name": "user", "path": "/home/u/.config/agentik/demo/config.yaml", "present": true, "travels": true},
  {"name": "repo", "path": "/work/site/.claude/agentik/config.yaml", "present": false, "travels": false},
  {"name": "env", "path": null, "present": true, "travels": false}],
 "settings": [
  {"key": "paint.colour", "value": "dark", "default": "light", "type": "string",
   "choices": ["light", "dark"], "summary": "The palette each painted line uses.",
   "source": {"layer": "user", "path": "/home/u/.config/agentik/demo/config.yaml", "line": 4},
   "change": {"kind": "edit", "command": null, "path": "/home/u/.config/agentik/demo/config.yaml",
              "block": "paint:\n  colour: dark", "note": null},
   "live": true,
   "values": [{"layer": "default", "value": "light"}, {"layer": "user", "value": "dark"}]},
  {"key": "width", "value": 80, "default": 80, "type": "integer", "choices": null,
   "summary": "The column a painted line is cut at.",
   "source": {"layer": "default", "path": null, "line": null},
   "change": {"kind": "command", "command": "agentik demo set width VALUE", "path": null,
              "block": null, "note": "Holds for this session only."},
   "live": true, "values": [{"layer": "default", "value": 80}]},
  {"key": "token", "value": "(set)", "default": null, "type": "secret", "choices": null,
   "summary": "The key the demo service is called with.",
   "source": {"layer": "env", "path": null, "line": null},
   "change": {"kind": "launch", "command": "DEMO_TOKEN=VALUE agentik demo paint", "path": null,
              "block": null, "note": null},
   "live": false, "values": [{"layer": "env", "value": "(set)"}]}],
 "warnings": [
  {"key": "paint.color", "reason": "unknown", "value": null,
   "path": "/home/u/.config/agentik/demo/config.yaml", "line": 9}]}
```

The answer counts only where `layers` and `settings` are lists and every setting is an object with a `key` that is a non-empty string; a layer, a warning or a `values` row that is not an object is dropped.

**Layers**, lowest first, every layer the tool reads whether or not its file exists.

| key | rule |
|---|---|
| `name` | from this list where it fits: `default` (what ships: code or a shipped file), `user`, `repo`, `local` (a repo file git ignores), `env`, `launch` (a flag or a profile named at start), `session` (this session only). **The user's file is named `user`**: the suite's list prints the first `user` layer's path beside the tool |
| `path` | the absolute path, or null where the layer is no file. A file the tool would read is named even when absent |
| `present` | whether the file exists; for `env`, whether any of its variables is set; `default` is true. The suite ignores it |
| `travels` | true for a file that is the user's own configuration and is worth carrying to a new machine: `agentik config --user-files` prints each such layer's `path` once. False for what ships, a repo's file (git carries it), state and the environment |

A name may repeat where a tool reads several files of one kind, one a folder: each row has its own `path`, and a `values` row of such a layer carries its `path` and `line`.

**Settings.** One row a leaf: a mapping is never a value, its leaves are keys.

| key | type | rule |
|---|---|---|
| `key` | string | a dotted path of `[a-z0-9_-]` segments, unique, stable. The suite cuts `<tool>.<key>` at the first dot, and past 20 settings groups the list by the first segment, so the first segment is the group a person would look under |
| `value` | string, number, boolean, null or a flat list | what the tool would use now, here. A secret is `"(set)"` or null, never its text |
| `default` | the same type, or null | the value on a machine where nothing is set: what ships and nothing else, so no file of the user's or of a repo, no variable and no flag. Where what ships is more than one layer, `default` is what they give together, so a new machine reads `0 changed`. The suite marks a setting as changed when `default` is not null and `value != default`, so the two are one JSON type: never `80` against `"80"`. Null where there is no default; such a key never reads as changed |
| `type` | string | `string`, `integer`, `number`, `boolean`, `list`, `path` or `secret`. The suite ignores it |
| `choices` | list or null | every value the tool takes, when the set is closed; the card prints them. Anything but a list reads as null |
| `summary` | string | one sentence under 100 characters: what the setting decides, in the present tense, for someone who has not read the code. It never opens "This setting" and never restates the key |
| `source` | object | the highest layer that sets the key. `layer` is a name of `layers`; `path` that layer's file or null; `line` the 1-based line the key stands on in that file, or null where the layer is no text file. Unset anywhere: `{"layer": "default", "path": <the shipped file or null>, "line": <its line or null>}`. The list prints `layer`; the card prints `path`, `:line` after it where given. Anything but an object reads as `{}` |
| `change` | object | all five keys, null where unused. `kind` `command`: `command` is the exact line, spelled `agentik <tool> ...`, the value as `VALUE`. `edit`: `path` is the file to edit and `block` the lines as they would stand in it, current value included, joined by `\n`, no final newline; the file is the one of the layer in force when a person can edit that layer, else the user's file, since an edit below the layer in force changes nothing here. `launch`: `command` is the start line with its flag or variable. `fixed`: `note` says why it cannot be changed. `note`, with any kind, is one sentence on what the change does not do. The card prints `command` for `command` and `launch`, `path` and `block` for `edit`, and for any other kind, or one missing its `command` or `path`, the fixed line with `note` |
| `live` | boolean | true when a change holds from the next read; false when it holds from the next session or the next start |
| `values` | list | `{layer, value}` for each layer that sets the key, lowest first, `default` among them where there is one. The card prints them in order. A row may also carry that layer's `path` and `line`: the card prints the `path` after the value, and `:line` where `line` is an integer |

**With KEY**: `settings` holds that one setting, or is `[]` when the tool has no such key, still `ok: true`, exit 0. The suite takes the setting whose `key` is KEY from `settings`; where there is none, it asks again with no key, under the same wall, to name the nearest. `layers` and `warnings` are whole either way.

**Warnings**, each `{key, reason, value, path, line}`. The suite prints each under the tool's list, a line and the file:

| `reason` | what it is | what the screen prints |
|---|---|---|
| `unknown` | a key in a file that the tool does not read | ``unknown key `<key>` ``, then `<path>:<line>` |
| `choice` | a value outside `choices`, with the `value` | `` `<key>` holds `<value>`, which is not one of its choices ``, then `<path>:<line>` |
| `unreadable` | `key` null: a file the tool skips because it cannot parse it | `` `<tool>` skipped this file: it could not be read ``, then `<path>`, `:<line>` where `line` is an integer |
| `ignored` | a key the tool knows and does not take from that file (a key that only a project's file may set, set in the user's) | `` `<tool>` does not take `<key>` from this file ``, then `<path>`, `:<line>` where `line` is an integer |

A `reason` of any other word, or one that is no string, prints the unknown-key line.

**A file that does not parse** is reported as the tool treats it. A tool that refuses to run on it answers §11.2's error, code `bad_file`, exit 2. A tool that skips the layer and goes on answers `ok` true with that layer `present` and one `unreadable` warning.

### §11.5 The doctor read: `doctor --json`

```json
{"schema": "agentik.doctor/1", "ok": true, "tool": "demo", "failed": 1, "warned": 0,
 "checks": [
  {"name": "python", "status": "ok", "detail": "3.9.6 at /usr/bin/python3", "remedy": null},
  {"name": "service", "status": "note", "detail": "no service is configured, so nothing was asked of one", "remedy": null},
  {"name": "launcher", "status": "fail", "detail": "the launcher is 1.1.0, older than the plugin's 1.2.0", "remedy": "/demo:install-cli"}]}
```

- `status` is `ok`, `note` (true and worth a line, nothing to do), `warn` (worth a look, never a failure) or `fail`. A thing that is not set up because the user never asked for it is a `note`, never a `fail`.
- `detail` is one line. `remedy` is one command a person can run, or null: a shell line, or a slash command (`/demo:install-cli`) where the thing to mend is the launcher a shell line would run. A line that works only inside the tool's checkout (`make install`) is no remedy. `name` may repeat. A check may carry keys of its own beside these four; the suite reads the four alone.
- An answer counts when it is one object of §11.2's doctor schema with `ok` true (from the `doctor --json` the suite asks, any `ok` but false) and `checks` a list of objects, each with a string `name`, a `status` of the four, a string `detail` and a `remedy` that is a string or null; one check of another shape and the whole answer does not count. `ok` false reads as one `fail` check, `doctor`, with the error's `message` and `remedy`. From the doctor read a describe names, the suite shows each `detail` and `message` as one line, cut at 300 characters, and reads as null a remedy holding a control or format character.
- A tool whose describe names no doctor read is asked `doctor --json`; where that answer ran and does not count, a second round asks plain `doctor`, and its exit alone is one check: 0 `ok`, else `fail`. An answer that is cut at 1 MiB, cannot start or is still running at the 30 s deadline, in either round, gets no second round and is one `warn` check. A doctor read that is named, ran and does not count gets no second round either: it is one `warn` check, as is one that is cut, cannot start or meets the deadline.
- `failed` and `warned` count the statuses, and `ok` is true whenever the read ran. The suite reads neither count: it counts the statuses of every check of every tool, its own first, prints those counts in its own `doctor --json`, and exits 1 when one check is `fail`, else 0.
- The exit and the text form stay the tool's own: the suite reads the object whatever the tool's exit was.
- The read ends inside 20 s whatever does not answer: a check that waits on a socket or a process has a timeout of its own. It never leaves this machine unless the user set up the thing it asks, and never writes outside the tool's own state.

### §11.6 A status read

A read the tool already has, named in `reads` by its argv. Where it prints an object, the object gains `"schema"` and `"ok": true` as its first two keys and keeps every other key as it was. The schema is `agentik.<tool>.<name>/1`, or `agentik.<verb>/1` for a verb the tool claims at the top level; a read that already carries a `schema` keeps it. A status read the suite draws prints one object, or a bare `null` for `unattended` alone; any other answer, a list among them, reads as `unreadable`. Where a read has nothing to read and exits non-zero with a line on stderr, the exit and the line stay.

The suite's `status` draws five names: `sessions`, `gate`, `backlog`, `run` and `unattended`, the last two into one part, the runs. It asks only the tools whose `agentik-<tool>` is on PATH (§11.1), a fallback table's tool among them. `agentik inbox` draws three names of its own, `questions`, `backlog` and `charter`, the same way: the fallback table's `inbox` lists first, for a tool on PATH, then the `status` reads of the other tools on PATH, the first read of a name winning. Of each name it runs the first read, the fallback table's tools first, then the others in name order; a second read of a name, and a read of any other name, is listed and never run. It adds words after a read's `argv` (for `backlog`: `--order` and the hq's `HANDOFF.md` where that file stands, then the checkouts), so the `argv` ends where the tool's own options and paths may follow. A tool the suite's fallback table names is read by that table's argvs and never asked `describe`.

A read still running at its wall reads as `timed out`, with no stderr line. A read counts with exit 0 and stdout one JSON object, or a bare `null` for `unattended`, which reads as no run. Else the source reads as `unreadable`, and the suite shows its stderr's first line, cut at 300 characters. The suite needs no `schema` and reads no `ok`; a `schema` that ends `/<n>`, `n` above 1, marks the part changed. The five names are those of the suite's own tools, and the reader pins each part's keys to that tool's answer: a read of another shape under one of them reads as changed, since a key missing or of another kind marks the part changed and its values null, and the rest is drawn.

### §11.7 What the tests of every tool hold, whatever its language

1. `describe --json`: exit 0; stdout is one object; every key of §11.3; no `ESC` byte; under 1 s.
2. Every read named in `reads` runs by `agentik-<tool>` plus its `argv` and prints one object with `schema` and `ok`, in a fixture that gives the read something to print (§11.6 names the cases with nothing).
3. The config read with no key, in a temp HOME with no file: every setting has every key of §11.4, no `source.path` lies under the temp HOME, and every `source.layer` and every `values[].layer` is a name of `layers`.
4. A user file that sets one key at a known line: that setting's `source` is `{"layer": "user", "path": <that file>, "line": <that line>}`, its `values` end with the user's, and the keyed read prints that setting alone.
5. The keyed read of a key the tool does not have: `settings` is `[]`, exit 0.
6. A user file with a key the tool does not know: one `warnings` row with its line.
7. A layer file that does not parse: `ok` false, `error.code` `bad_file`, the file in `error.message`, exit 2; or, in a tool that skips such a file, `ok` true and one `unreadable` warning naming it.
8. After every read but the doctor read: the temp HOME outside `$XDG_CACHE_HOME/agentik/` holds the files it held before, byte for byte, `~/Library/Caches` among them. The doctor read may add files under the tool's own state folder and nowhere else.
9. Every `summary` is one sentence under its bound, and no two settings share a `key`.

## §12 The records root: where a repo's working records are (hq design/28)

A repo's working records (its charters, packets, build order, wish list and open questions) live in its own tree unless the clone says otherwise. One key in the clone's own git config, `agentik.records`, names a folder outside the clone that holds them, each record at the path it has in a repo today. It is set when `git config --local --get-all agentik.records` finds it, and read as `git config --local --path --get agentik.records`, so a worktree sees the main checkout's value, git expands a leading `~`, and neither the user's file, the environment nor a worktree's own file can state it. A public repo also tracks one line that says its records live out: `records: out` in `.hygiene-allow`. The line counts only in the file as committed at `HEAD`; an untracked or uncommitted line says nothing. `.claude/agentik/config.yaml` declares nothing here until the suite's layer reader knows a `records` key.

`scripts/agentik_records.py` is the one resolver, stdlib at Python 3.9; `sync` places it at `plugin/lib/agentik_records.py` (§10) and the suite holds a byte-equal copy. `resolve(folder)` answers the object `agentik.records/1`: `repo` (the main checkout, as git names it), `records`, `holder` (the top of the git repository whose working folder holds `records`, or none), `prefix` (`records` relative to `holder`), `state` and `why`. A folder in no git checkout raises `NoRepo`. Its cases are data, `tests/records_cases.json`, one layout a case, so a tool in another language runs the same table.

| state | when | records |
|---|---|---|
| `own` | no key, and the tree does not declare its records out | the top of the working tree the call stands in, so a worktree's records ride its branch |
| `out` | the key resolves | the key's folder; git acts on a record run in `holder` |
| `unset` | the tree declares its records out and the clone has no key (`why` is `no-key`) | none: write no record and ask for none |
| `broken` | the key is set and does not resolve | none, and never the repo's root; refuse each record read and write |

A key that is set is never `own` or `unset`: set once with a value git's `--path` read cannot give, it is `unread`; set more than once, `many`. The key resolves when its value is absolute (else `why` is `relative`), names a folder that is there (`missing`), lies outside the main checkout and every worktree of the clone (`inside`), ends in the main checkout's folder name (`name`), and sits in a holder whose own tree does not declare its records out (`holder`). Outside is judged by the file system, not by spelling: no folder from the records folder up to the root may be the same file as the main checkout's top or a worktree's, so another case or the data volume's path does not get in, and a repository that shares the clone's git folder, a moved worktree among them, is `inside` too. The name is the real folder's, as its parent lists it, so a link named as the clone does not pass. A private repo may set the key without the line; it is then `out` with no guard.

`agentik records [--json] [DIR]` prints the object for DIR, the working folder by default, and writes nothing: plain, one line a key, `why` as a sentence; `--json`, the object alone. It exits 0 in every state, and 2 for a DIR that is no folder or in no git checkout. `agentik doctor` gives the repo it stands in one row, `records`: `ok` in `own` and `out`, `warn` in `unset`, `fail` in `broken`, every state but `own` by name with its reason. A `broken` line names the key and its values, cleaned as every value on screen; an `out` with no holder says nothing is committed.

**The guard.** `scripts/hygiene` holds a declaring repo's records out of its tree and its pushes with one judged group, `records`. The declaration is read by the resolver's rule exactly: a line that is `records: out` but for trailing white space declares, and is no allow row; any other line naming the group `out` (`records: out # why`, `records:  out`, an indented line) and any row naming `records` is a bad entry, exit 2, so the two readers never differ in silence. In a tree that declares, in the working `.hygiene-allow`, the one at `HEAD` or an `--allow` file, so an uncommitted removal of the line does not switch the guard off, each scanned path (tracked, or untracked and not ignored) under a record name is a hit no row excuses: `history/`, `design/packets/`, `bugs/`, `HANDOFF.md`, `NICE_TO_HAVE.md`, `OPEN-QUESTIONS.md`, `relay/queue.yaml` and `.hygiene-live`, each at the root, the names case-folded, since a case-blind file system holds `History/` as `history/`. Under `--commits`, each path a commit adds or modifies under a record name is a hit where the range's tip or its base declares, each read from its own `.hygiene-allow` blob, and a merge's paths against its first parent count as any commit's (the other groups still skip a merge's diff); a base that declares with a tip that does not is a hit on `.hygiene-allow`, so the push it would refuse cannot switch the guard off. Read for the declaration alone, an allow file never fails a scan: a symlink or other entry that is no regular file declares nothing, and bytes that are not UTF-8 are read as the resolver reads them; the read as rows fails as it always has. The resolver and the scanner both read git with `--no-replace-objects`, so a replace ref moves neither. The group counts, as every group, and shows only where the scan declares. The guard runs where the scanner runs: each `make check`, the landing's and the publish's scans (§6), and a pre-push hook where the repo has one; a hand push in a repo with no such hook is not scanned.

**The cut.** `scripts/records-cut --repo <clone> --holder <repo> [--go]` moves a repo's records out: each path at `HEAD` under a record name goes to `<the holder's top>/repos/<the clone's folder name>/` at its own path, the folder the key must name. Without `--go` it is a dry run that writes nothing: it prints the records counted by name, the destination, every refusal that applies and the plan. It refuses a clone that is no main checkout, is dirty, has no upstream or is ahead of it, has a branch or worktree with a record commit past `HEAD`, a record that is a symlink or under one, a key or a declaration already, or a `scripts/hygiene` other than commons'; and a holder that is no repo, is the clone, is dirty under the destination, already holds files there, or declares `out` itself. `--go` copies each blob with its mode and checks its sha256, makes one commit in the clone that removes the records and adds `records: out`, sets the key, and proves the move with the resolver, the clone's own scanner and a compare of the two trees; it never commits in the holder or pushes. It ends with the holder's commit line and the push order: the clone first, then the holder.
